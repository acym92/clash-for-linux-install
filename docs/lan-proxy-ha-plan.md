# 局域网多订阅代理优化计划

状态：第一阶段已实现。日期：2026-09-05。已包含多订阅内联节点聚合、阈值/冷却切换、故障恢复、人工保持与固定、局域网代理和客户端订阅服务；远程 `proxy-providers` 聚合、隔离下载测速及双机高可用仍属于后续范围。

## 1. 目标与部署边界

在局域网 Linux 主机部署统一代理入口。其他设备始终连接这台主机，由服务器统一管理多个上游订阅、检测节点、选择出口。默认采用 Mihomo + systemd，第一版明确限定该组合，其他内核和 init 系统保留原功能，后续再适配自动优选。

优先级：实际可用 > 连接稳定 > 延迟改善 > 下载速率改善。延迟接近时保留当前节点，持续明显变差才切换，故障时优先恢复服务。

单机方案提升的是上游节点与代理进程的可用性，不能消除 Linux 主机断电、局域网断开、路由器或宽带故障。若未来要求服务器本身高可用，需另行设计双机、虚拟 IP 和独立故障域；双机也不能自动迁移已有代理连接。

## 2. 客户端如何接入

区分两个地址：代理地址实际转发流量；订阅地址只用于下载客户端配置。

- 固定代理入口：例如 `192.168.1.10:7890`，支持 HTTP/SOCKS5，配置代理认证。
- 可选配置订阅入口：例如 `http://192.168.1.10:8088/sub/<设备令牌>`，向兼容的 Mihomo/Clash 客户端返回配置。生产使用是否启用 HTTPS 取决于局域网信任边界与证书部署条件。
- 下发配置只包含“局域网代理服务器”这个节点，指向 Linux 的代理端口；不下发真实上游订阅、上游节点或管理 API 密钥。
- 客户端配置必须让预期代理流量经过服务器节点，局域网流量保持直连；订阅更新也应通过局域网直达服务器，避免循环依赖。
- 不运行代理客户端的设备，可手工设置 HTTP/SOCKS 代理；只有遵守代理设置的应用会生效。透明网关/TUN 接管属于独立后续功能，不在首版默认部署范围。
- 各设备使用独立订阅令牌和代理凭据，支持撤销；订阅令牌与代理凭据分开管理。兼容性按实际客户端测试，不能假定一个配置可用于所有客户端。

部署时固定服务器 LAN 地址；代理端口与订阅端口仅允许指定局域网网段访问。内核控制 API 默认绑定回环地址，远程管理另设受限入口。订阅响应禁用公共缓存，日志不记录令牌和凭据。

Mihomo 官方配置支持 `allow-lan`、绑定地址、允许网段和代理认证：[全局配置](https://wiki.metacubex.one/config/general/)。

## 3. 核心架构

```text
局域网设备 ──固定代理地址──> Mihomo LAN 入口
                                  │
                           统一规则 → HA-出口（select）
                                  │
                    A / B / C 订阅中的具体叶子节点
                                  ↑
                     优选进程：探测、决策、API 切换

订阅管理 → 下载/转换/校验 → 分订阅节点集合 → Mihomo
配置订阅服务 → 给客户端下发固定 LAN 入口配置
```

所有订阅同时进入候选池，出口选择落在具体叶子节点，状态记录节点所属订阅。服务器统一维护规则、DNS、监听端口和出口组，不直接叠加各订阅携带的整套规则。节点名称加订阅标识，稳定 ID 与展示名分离，处理同名、重命名和订阅间重复节点。

对于只有 `proxy-providers` 的上游配置，也必须解析或管理其集合，不能只提取 `.proxies` 而得到空订阅。节点协议、远程集合路径和目标内核版本需要兼容性校验。

优选进程是 HA-出口的唯一自动决策者；组内不嵌套会独立换节点的自动组，以免绕过冷却时间和人工固定。可以复用内核探测能力，但不让另一套策略同时决定出口。

官方 `url-test` 提供切换容差，适合简单延迟优选，但本需求还包括连续确认、相对阈值、人工控制和下载速率保护，因此采用显式调度器与 `select` 组：[自动选择](https://wiki.metacubex.one/config/proxy-groups/url-test/)、[手动选择](https://wiki.metacubex.one/config/proxy-groups/select/)。

## 4. 默认探测与切换策略

以下参数为首轮部署起点，必须根据真实线路观测调整，不是可用性承诺。

| 项目 | 初始默认值 | 目的 |
| --- | --- | --- |
| 当前节点与热备探测 | 每 15 秒 | 快速发现故障 |
| 全量节点探测 | 每 5 分钟，错峰执行 | 发现恢复或新出现的优质节点 |
| 热备集合 | 3～5 个，尽量覆盖不同订阅 | 减少单订阅故障影响；不假定不同订阅一定独立 |
| 单次探测超时 | 3 秒 | 限制坏节点拖延 |
| 延迟统计 | 最近 5 次结果的中位数 | 抑制一次抖动；失败单独统计 |
| 性能切换确认 | 连续 3 轮满足改善条件 | 避免偶然低延迟触发切换 |
| 性能切换冷却 | 上次切换后 10 分钟 | 降低频繁换出口 |
| 故障确认 | 连续 3 轮确认不可用 | 降低误判；故障绕过性能冷却 |
| 故障节点重新入选 | 连续 3 轮成功 | 防止刚恢复就来回切换 |
| 上游订阅刷新 | 每 1 小时，加入随机错峰 | 刷新节点列表，与节点探测分开 |

每轮采用两个可配置、相互独立的轻量 HTTPS 目标；至少一个正常时不直接判定节点全坏。目标级故障需跨节点对照识别，并剔除故障目标对排名的影响。排名必须比较同一目标、同一时间窗口的有效样本；样本不足时维持当前节点，不能把超时当作 0ms。通用探测不能保证所有业务站点可用，必要时添加目标业务探测。

限制并发，任务不重叠，优先服务当前节点和热备的探测。节点过多时对全量扫描设置时间预算和队列，不让扫描阻塞故障处理。切换前对热备再做一次新鲜探测。

### 4.1 延迟接近：保持当前节点

记当前延迟中位数为 Lc，候选延迟中位数为 Ln。仅当以下条件全部满足，才进行性能切换：

1. 候选节点健康，近期失败率不高于当前节点，样本足够且新鲜。
2. `Lc - Ln >= max(80ms, Lc × 30%)`。
3. 同一候选连续 3 轮满足条件；候选变化需重新确认。
4. 距离上次切换至少 10 分钟，且未被人工固定。

例子：当前 150ms、候选 120ms，不切；当前 200ms、候选 100ms，持续满足条件后切；当前 500ms、候选 400ms，不切；当前 500ms、候选 200ms，持续满足条件后切。

持续严重劣化可启用快速通道：当前延迟连续 2 轮超过 1000ms，且候选低于 500ms并至少改善 50%，允许绕过性能冷却。若全网都慢而没有明显更好的节点，保持当前出口并记录状态，不盲目切换。

### 4.2 当前节点不可用：故障切换

连续 3 轮两个目标均失败，且存在经复测可用的热备，切换至健康热备，不受性能冷却限制。15 秒间隔对应约 30～60 秒故障检测与恢复目标，实际取决于故障发生时刻、探测超时与调度负载；必须实测。

如果所有节点都失败，进入“全部不可用”状态，保留最近配置并持续退避重试；不反复轮换，不把需要代理的流量静默改成直连。订阅更新服务、DNS 和本地网络故障需要单独诊断。

恢复后的旧节点也必须重新达到改善阈值才允许切回，不因其恢复就抢回出口。

### 4.3 下载速率：辅助筛选

保留前一轮需求中的下载速率能力，但默认不因带宽更高单独触发换节点。先实现可用性与延迟策略，再增加有限下载测试。

- 仅对延迟优选后的少量候选测速，错峰、串行下载，避免相互抢占带宽。
- 示例预算：每 60 分钟最多 3 个候选、每个最多 5 秒/5MiB、每日最多 200MiB，任一预算触顶即停止；此结果只是短时速率估计。
- 业务高负载时跳过主动带宽测试。通过独立本地测试入口或隔离测试实例固定到候选节点，不切换正式出口来测速；测试流量排除在业务负载判断之外。
- 多次确认候选吞吐明显差于当前节点时，可否决非故障性能切换；没有新鲜速率结果时回退到可用性与延迟判断，状态明确标注“速率未知”。
- 故障恢复优先，不等待下载测速结束。

## 5. 使用过程中尽量不打断

运行期换出口只更新 `HA-出口` 的 API 选择，不调用现有 `sub use` 整套配置切换路径、不重启主内核、不清空全部连接。

设计目标是让新连接走新节点，已建立连接尽量沿旧节点结束。具体 TCP、UDP、QUIC、连接复用及 provider 更新行为须对选定 Mihomo 版本做集成验证，不能承诺所有连接绝不中断。旧上游已经故障时，其连接不能无缝迁移，依赖客户端重连；同一应用后续新连接的公网 IP 也可能变化。

提供两类人工模式：

- 稳定模式：暂停性能优化切换，节点故障仍允许切换，适合会议、长下载等场景。
- 严格固定：固定指定节点，包括故障也不自动换；明确展示可用性取舍，可设到期自动解除。

面板手动选择与后台自动调度必须有一致的控制规则。非调度器产生的选择变化应进入人工保持状态并记录来源，不得下一轮立即覆盖；未知来源变更也需按人工保持处理。

## 6. 启动、更新与异常恢复

启动时先使用最后一次通过验证的配置和持久化出口，不等待所有订阅联网更新。API 就绪后，优先探测当前节点及热备，再后台刷新订阅和全量评估。首次没有缓存则先获得一个可用候选并开始服务，其余后台继续发现；全部失败时明确报告并重试。

订阅下载成功只表示更新可用；订阅下载失败不代表缓存节点不可用。每个订阅独立保存最后成功配置、更新时间、错误与重试计划。到期和流量信息作为辅助信号，以实际探测决定是否可用。

更新采用临时文件 → 转换/校验 → 原子替换 → provider 刷新 → 实际运行验证。空响应、格式错误、暂时下载失败不得覆盖旧缓存。部分订阅失败不阻塞其他订阅。失败使用有上限的指数退避，成功后恢复正常刷新周期。

订阅删除当前节点时，先准备健康替代，再变更候选池；若旧节点仍可用，可短时保留待现有连接结束，设置最长保留期。实际 provider 更新是否影响已有连接必须验证。失败时恢复最近成功文件并确认运行内核实际状态，不能只恢复磁盘就宣称成功。

优选服务由 systemd 管理，自身崩溃自动重启，单实例锁避免重复运行；内核重启后等待 API 就绪再协调期望选择与实际选择。调度器短时退出时，Mihomo 保持当前选择继续转发，但此时没有自动故障切换，应显示为管理功能降级。持久化冷却时间和人工保持状态，避免重启绕过策略。

## 7. 对现有项目的改动

以下新增文件和命令均为拟议接口，当前尚不存在。

| 位置 | 优化内容 |
| --- | --- |
| `scripts/cmd/sub.sh` | 复用下载、转换、锁和元数据；增加聚合模式，更新活跃订阅时不再调用整套重启；保留旧单订阅模式 |
| `scripts/lib/config.sh` | 新增统一配置生成；管理多个 provider、稳定节点标识及 HA-出口；校验实际规则经过预期出口 |

| `scripts/ha/`（新增） | 探测、状态机、候选排名、持久化、单实例互斥、日志；具体运行时在实现阶段决定 |
| `resources/ha.yaml`（新增） | 阈值、时间间隔、探测目标、预算、人工策略等配置 |
| `scripts/init/` 与安装/卸载流程 | 注册及清理优选服务、配置订阅服务，覆盖开机自启及 `clashctl on`；服务职责分开 |

不要直接拼接现有面向终端的测速输出作为决策输入。API 超时、鉴权失败、内核未就绪与节点探测失败必须区分；切换返回成功后读取实际选中节点核验。

## 8. 实施顺序

1. **统一入口与聚合**：固定 LAN 代理、访问控制、三订阅节点池、统一规则、订阅缓存、客户端配置订阅。先允许手工选择，验证各设备确实经过 Linux 出口。
2. **只观测不切换**：增加探测、状态记录和模拟决策，运行 24～48 小时，核实超时比例、目标可靠性与阈值；订阅 URL 和凭据全程脱敏。
3. **故障自动恢复**：实现热备、故障确认、冷却绕过、全部不可用处理、启动恢复与服务监督；先启用故障切换。
4. **稳定性能优选**：启用连续改善阈值、严重劣化快速通道、保持/固定模式、API 切换和现有连接验证。
5. **下载速率与调优**：增加隔离测速、流量预算和低吞吐保护；根据观测调整默认参数。

每阶段都应可关闭 HA 模式回退至原管理方式；回退涉及配置重载或重启时明确提示影响，不承诺无损回退。

## 9. 验收标准

| 场景 | 预期行为 |
| --- | --- |
| 客户端导入服务器订阅 | 只获得 LAN 入口；上游换节点后客户端无需更新配置 |
| A 订阅下载失败，但缓存节点正常 | 保持服务，独立重试，不判定整订阅节点失效 |
| 当前 150ms，候选 120ms，持续一小时 | 不因延迟自动切换 |
| 当前 300ms，候选 100ms | 满足连续确认和冷却条件后切换 |
| 当前偶发一次高延迟或超时 | 不立即切换 |
| 当前节点持续不可用，热备正常 | 达到故障确认条件后切换，测量实际恢复耗时 |
| 冷却期间再次发生真实故障 | 允许故障切换；无健康替代则停止轮换 |
| 一个探测站点全局故障 | 不引发全体节点误判和切换风暴 |
| 所有上游不可用 | 清楚显示失败、持续恢复探测，不静默直连 |
| 性能切换时运行长 TCP 下载、会议、QUIC | 核验连接行为；记录无法保留的协议/场景；不清空全部连接 |
| 空订阅、节点重名、嵌套 provider、当前节点删除 | 无名称串线，不覆盖成功缓存，状态与内核一致 |
| 重启 Linux、内核或优选进程 | 缓存可启动、状态可恢复、没有重复调度器 |
| 人工保持/严格固定及面板手动选择 | 按模式执行，不被后台偷偷覆盖 |
| 无令牌、已撤销令牌、非允许网段 | 不能获取配置或使用代理；管理 API 不对 LAN 普通客户端开放 |

验证包括策略边界的确定性单元测试，以及 Linux 上真实 Mihomo 的集成测试；带宽、连接持续性和故障恢复必须实测，不能只靠模拟测试判断通过。

状态页/命令至少展示：当前订阅和节点、健康/降级状态、延迟窗口、速率及其采样时间、热备、新鲜度、失败次数、最近切换原因、冷却剩余时间、人工模式、订阅最后更新结果。每次自动切换记录前后节点与触发证据，方便解释“为什么切换”。
